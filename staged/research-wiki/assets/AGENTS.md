# 科研知识库 · agent 维护规则

这是一个 LLM Wiki。知识以本目录下互链的 Markdown 页面为本体，由 agent 编译和维护，作者阅读、签核、备注。改任何页面前先读完本文件。

它是写给 agent 读的说明书，不是执行平台：页面写清每样东西是什么、什么时候用、需要什么数据、代码怎么改；agent 读懂后在作者当前课题的环境里自己写代码、运行。图模板带可运行代码并经回放验证；分析方法是笔记，可附可复用的代码模板。开发期可在既有隔离环境对显式函数入口做调用与收据验证（不安装依赖、不代跑作者课题）；页面或网页不替作者运行课题分析，代码存在、一个分支通过或软件夹具通过都不等于科学有效。

## 当前收录范围

复刻与新收录只接受一个逻辑 panel。先识别去重样式，再询问代表单 panel、数据及关键细节并确认计划；完整原图只读保留在画廊用于溯源，不作为 Wiki 条目或复刻交付目标。现有整图来源已归档并在前端隐藏，保留其来源记录及既有单 panel 模板。图库保留“单 panel 图样”和“可调用模板”两个可重叠浏览入口。

## 三层

- **原始层（只读）**：科研绘图画廊（路径见 research-wiki 技能的 `config.json` 里的 `gallery_root`）。每张复刻图是一个条目，`meta.json` 是事实来源。第二版会加入 Zotero、笔记、PDF。不改原始层，签核状态除外（只能通过 `wiki.py` 或网页修改）。
- **wiki 层**：本目录。agent 编译的页面。
- **规则层**：本文件。

## LLM Wiki 模式（Karpathy 可定制，不是认证标准）

原文：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f 。本库按本地边界落地，不声称存在认证标准：

- **三层**：原始层（画廊、`source/`、`original_code/`，只读保留字节/哈希）→ 编译层（本目录互链 Markdown，agent 写的理解）→ 规则层（本文件与 `research-wiki` 的 references）。
- **操作**：`ingest`（收录/更新）、`query`（查模板/方法/课题）、`lint`（结构、断链、状态、重复家族）。写操作最后 `save`。
- **更新而非堆叠**：新来源先判断能否更新已有方法家族或图样；不按“一个来源一个方法/一张图”新增同义页。结构相同不等于科学直连，语义关系只在方法侧维护一次。
- **记录不确定**：页面保留来源、矛盾、未知项、未运行/未验证分支和作者备注；不把来源摘要当成已验证结论。
- **索引与日志**：`index.md` 每页一行摘要，由脚本重建；`log.md` 只追加；不手改 facts/status/user 区块。
- **查询回填**：课题中得到的可复用判断、失败模式和适配动作，按作者确认回填页面“使用记录”或 `projects/`，不留在对话里。
- **不引入**：数据库、向量库、网页代码执行器或自动安装；网页只读展示和记录状态。

详见 `research-wiki` 技能的 `references/llm-wiki-mode.md`。

## 页面类型

| 目录 | type | 内容 |
|---|---|---|
| `layouts/<id>.md` | layout | 一个逻辑 panel 来源，记录所含模板；历史整图仅保留归档记录。`<id>` 与画廊条目 id 相同，签核状态在这里 |
| `layouts/<id>/` | — | 版式资产：`thumb.png`；可选的版式回放另有 `layout.json`、`example/`、`preview.png`、`verify/` |
| `templates/<id>.md` | template | 一个逻辑 panel 模板，可单独套用。沿用 `<版式 id>--<图型>` id；结构变体默认分属不同代表条目，可被多个版式引用 |
| `templates/<id>/` | — | 模板资产：`spec.json`、`code/`（含 `panel.py`）、`example/`、`preview.png` |
| `methods/<id>.md` | method | 方法笔记（一步分析）：用途、适用/不适用、输入、怎么做、代码、输出成哪个接口、来源与许可证 |
| `methods/<id>/` | — | 方法资产（都可选）：`source/`（原代码归档，只读）、`code/`（可复用代码模板） |
| `interfaces/<slug>.md` | interface | 数据接口：一种标准表格（列名、类型、必需/可选、含义）。方法最后整理成它，模板读取它 |
| `chart-types/<slug>.md` | chart-type | 图型概念页：回答什么问题、何时选它、与相近图型区别、常见误用 |
| `projects/<slug>.md` | project | 课题页，记录用过哪些模板、成图在哪 |
| `index.md` | — | 脚本生成的目录，不要手改 |
| `log.md` | — | 只追加的操作日志，不要手改 |

## 方法家族、实现与验证（2026-10-23）

- `method_kind` 决定默认入口：`analysis`（分析家族，默认方法目录/推荐）、`workflow`（组合流程资料）、`technical`（源码/绘图接口等技术资料）。旧页未分类时保持可读但不自动推荐，先由 agent 分类。
- `summary` 是一句可用于索引的判断性摘要；`data_contract.input/output` 写真实对象/矩阵/模型与结果含义，不强制所有输出 CSV；`inputs/outputs` 只列真实接口，可以为空。
- 具体实现写在 `implementations`：`id`、`title`、`language`、`entrypoint`（`code/...:函数`）、`dependencies`、`verification`。原始代码仍在 `source/`，保留原语言、原字节和哈希；`code/` 是显式参数化/封装版。
- 验证收据 `verification/*.json` 至少含 `schema_version=1`、`implementation`、`state`、`scope`、`command`、`checks`、`environment`、`files`（覆盖当前 `code/` 全部源文件的 SHA-256）。`passed` 只写实际执行且检查通过的分支；缺依赖/上游失败写 `not_run` 并保留精确错误，不安装、不伪造。任一代码变化使旧收据失效。
- 推荐门槛：`method_kind=analysis` + 作者 `ready` + 笔记完整 + 至少一个当前 `verified` 实现；`ready_for_use` 另查实现，`status=ready` 本身不授予执行能力。一个 verified 分支不批准其他分支；`workflow`/`technical` 不进入分析推荐，也不要求分析实现收据。
- 代码查看器与 `code-files` API 从同一 `implementation_status` 按入口文件派生逐文件分支状态：共享文件列出全部分支和 scope，混合状态显示 `mixed`；原始版保持来源状态，没有 receipt 的分支不提升。
- 旧 SCP/课题实现页保留旧 id、`source/` 和作者备注，改为来源/实现资料并链接真正家族；语义 `figure_relations` 迁往家族，原页不再作为主记录。结构相似、接口同名或标签相同都不构成 direct。

## 最小运行闭包与独立性证据（2026-10-23）

- 每个具体实现/模板用资产根目录的 `runtime.json` 声明运行事实；解析、路径校验和状态派生只在 `rwiki/runtime_contract.py` 一处实现，API、lint、check-entry、代码查看器与前端使用同一事实。
- 字段：`schema_version=1`、`kind`（method/template）、`id`；方法为 `implementations[]`，模板为单对象。每项含 `id`、`entry`（`code/` 下）、`entry_function`、`language`、`runtime_mode`、`files`、`resources`、`required_packages`、`optional_packages`、`python`、`source`、`evidence.portability`。
- `runtime_mode=standalone`：只需清单内的局部调用闭包；`bundle`：仍需完整来源库；`unknown`：历史未审计。声明不是验证。
- 独立性状态：`verified`（异目录复制、新进程、不提供来源库路径、实际调用并通过）、`declared`（只有声明）、`not_run`（执行到精确缺依赖/上游失败）、`stale`/`invalid`（清单、入口、helper、资源或依赖声明变化）、`bundle`、`unknown`。
- 独立性与算法验证是两个轴：`verification/*.json` 的 `verified`/`not_run` 仍只由实际算法调用决定；`portability=verified` 不授予算法 `verified`，算法通过也不证明可独立迁移。
- 清单路径限于资产目录：拒绝绝对路径、越界、隐藏路径、缺失文件、重复项和符号链接逃逸。API 只读，不扫描课题任意目录，也不把服务器已安装包当作课题环境。
- 来源整库只用于原始溯源和审查对照；复制到课题时只带清单指定的文件与资源。成熟包自身的传递依赖保留；可选包按功能延迟检查。缺包保持精确 `not_run`，不安装。
- 入口可接受旧 `bundle` 参数以兼容旧调用，但不得读取整库；无法兼容时保留旧实现并新增独立分支。source 一个多入口文件时，加载不得检查其他分支的可选包。
- 清单、入口、helper、资源或依赖声明变化使独立性证据过期；算法代码变化使算法收据过期。旧证据保留，不改写成重新执行。
- 每个入口必须封装在模块私有闭包中，只向 source 环境暴露入口函数；模块路径取当前被 source 的文件（最内层 `ofile`），不得取外层课题 driver，也不得把 engine/helper 放成多个模块共用的全局名。`source(local=env)`、嵌套课题 driver source、多个模块同一环境先后加载后分别调用都必须工作。
- 调用前后必须恢复 `search()` 与 options：只 detach 本次新增的包，按依赖逆序重试；用户原有已 attach 的包保持；成功和异常路径都要检查，diagnostics 不得在未恢复时写“none”。
- 声明的每个 `resource` 必须同时列入 `files` 并核对 sha256；清单入口的 `entry`/`entry_function` 必须与页面 `entrypoint` 路径和函数一致，否则独立性证据无效。`resources`/`source`/`packages`/`evidence` 容器非法时返回具体清单错误，不能让 API 500 或把错误清单当普通未审计。
- 算法收据的 `passed` 只能由实际运行日志、输出断言和比较结果派生；命令必须是含实际目录/case/输出的可重放命令，收据记录输入/输出哈希与执行时代码哈希。不得用硬编码配方或旧输出重绑新代码哈希。
- Monocle2/3 等复合实现分开分析核心、对象适配和可选绘图；核心不依赖 Seurat/绘图，不交互、不猜根（`root_state`/`use_partition` 显式），可选功能包只在对应入口检查。
- 运行函数不等于分析实现：纯绘图/辅助函数不得写入 `analysis` 页的 `implementations`，也不计入算法 `verified` 或推荐门槛；可放已有技术资料或正文辅助说明。分析核心、对象适配、绘图各自声明能力与验证范围。

## 研究领域与分析用途（2026-10-23）

- `tags` 继续表达研究领域（既有受控大类）；`analysis` 页新增 `purposes` 表达分析用途。两者是两个维度，不做互斥父子目录，也不新造重复的 `domains` 字段。
- `purposes` 词表只维护在 `rwiki/method_taxonomy.py`：预处理与质量控制、降维与聚类、整合与批次校正、注释与参考映射、差异与功能分析、轨迹与动态分析、模型评价、模型解释。新增用途须同时更新词表、文档、测试和迁移记录。
- 一页可有多个领域和多个用途；所有入口引用同一 `id` 与规范页。计数是去重页数，重叠分类之和不等于方法总数，不能把各分类计数相加当方法数。
- `GET /api/method-taxonomy` 与 `lint` 从同一函数派生词表和计数；前端不复制第二套词表或筛选逻辑。领域/用途只用于发现，不作为科学适用性或可执行推荐的硬门槛。
- 缺 `purposes` 的旧 `analysis` 页保持可读；`lint` 与 `check-entry` 提示补充，不退回作者状态、不伪造验证。非法用途或重复用途是 ERROR；非 analysis 页写 `purposes` 也是 ERROR。
- 分类元数据变化不使实现验证收据失效；笔记验收指纹变化时重录验收，不代签。

链接一律用相对本目录根的双链：`[[templates/<id>|显示名]]`、`[[layouts/<id>]]`、`[[interfaces/shap-summary]]`。frontmatter 里的列表字段（`tags`、`purposes`、`keywords`、`chart_types`、`templates`、`layouts`、`panels`、`inputs`、`outputs`）存的是值，不是链接；来源/互补关系靠正文链接表达；方法—图语义关系在方法侧 figure_relations 唯一维护，反向自动派生。

## 标签与关键词

- `tags` 只写受控大类，用于图库/方法库的领域筛选：值取自 `config.taxonomy` 指向的 `scenario_taxonomy.yaml` 单一受控词表的规范键/标签（本文不复制固定清单）。不得写数据集 ID、模型/软件名、图型细类或自由方法名。
- `purposes` 只用于 `analysis` 页，值必须来自上述单一词表；不要写自由方法名、模型名或数据集。领域与用途可多选，同一页仍只有一个规范入口。
- `keywords` 写具体检索词（如 GSE251716、SHAP、LightGBM、dotplot、marker、pathway、proportion、Seurat、DoubletFinder）；它们在 facts 的“关键词”行显示并参与搜索，但不进入标签下拉。
- 收录时，画廊 `scenarios.primary/secondary` 的受控标签进入 `tags`，`scenarios.free` 进入 `keywords`。方法页由 agent 手写 tags/keywords，遵守同一清单。
- `lint` 会把不在受控词表中的 tags 报为 ERROR；`purposes` 的非法值、重复值和非 analysis 页使用也报 ERROR，缺用途只报 WARN。领域词表只维护在 `config.taxonomy` 指向的 `scenario_taxonomy.yaml`（跨域扩展版已随跨领域批次采纳）；新增类别需先改该受控词表再迁移页面。词表扩展只声明领域词汇，不意味着相应领域已有实现或已验证方法。`purposes` 词表独立维护于 `rwiki/method_taxonomy.py`，新增用途须有实际的作用域设计与测试证据，不为填满分类而添加。

一张图或一个方法能用在哪里，写在“适用”节：它回答什么问题、需要什么形状的数据，与学科无关。

## 什么能进知识库

- 版式页只能由 `wiki.py ingest-figure` 根据画廊条目生成；画廊条目只由 sci-figure-replica 复刻产生。panel 模板只能从已签核的版式拆出（`scaffold-template`）或复用（`attach-template`）。不得手工新建这两类页面，也不得为没有复刻过的图写页面。`lint` 会报告找不到画廊条目的版式、来源不明的模板。
- 图型页只在收录复刻图时自动补齐；课题页只由 `record-use`（配图使用）或 `record-method-use`（仅分析使用，登记到"使用的方法"，不产生图/不写图页）生成。
- 方法笔记由 agent 用 `scaffold-method` 建骨架后编写，来源可以是帖子代码、作者课题脚本、GitHub/论文代码，或 agent 依据文献与官方文档编写（`--written`，必须写 `cite`）。
- 常规单次统计检验（t 检验、Wilcoxon/Mann–Whitney、卡方、单因素 ANOVA 等）本身不作为独立方法页收录。把它们写进所属分析方法页的“怎么做/输出”或图注的统计说明；只有当页面讨论的是特定研究设计下的估计量、重采样/验证方案、多重比较校正、效应量或实现边界时，才单独成页。判断标准是可复用的分析设计与实现边界，不是检验名称。

## 先咨询样式与范围

输入文章、图或代码时，agent 实际读图后列去重样式卡：代表裁图、原图/bbox 与重复位置、视觉编码、附属结构、已有模板/差异、不确定点。每个选定样式只做一个代表单 panel；模型/指标/单位/颜色变化通常作为参数，编码或结构实质不同才保留可选变体并说明理由。inset、色标、边缘分布和必要共享标注随主 panel，多 axes 不等于多个模板。图片数、哈希或图型名均不能代替样式判断。

在渲染或正式收录前，集中明确选定样式/代表、数据来源、保真重点、语言/代码及交付计划；复用已有答案。缺原始数据先说明缺口及影响，询问作者本次用估读还是合成并等待选择。完整原图/哈希只读保留，选定裁图与原图 bbox 另记；未选 panel 不构成本轮覆盖要求。完整整图只在画廊只读保留作溯源，不再复刻整组或新建整图 Wiki 条目。历史整图来源通过 Wiki API 归档并在前端隐藏，保留历史模板的出处。

方法联想限定为有依据的方法家族推广（如 XGBoost＋SHAP → 满足条件的机器学习模型＋SHAP）：保留原实现，说明适用范围、前提、限制与未实现/未验证分支；不从画法通用性推导宽泛新分析方法。先写文字，有来源代码可按函数契约融入，不自动补算法。

## 谁能改什么

- `<!-- user:start -->` 与 `<!-- user:end -->` 之间是作者的内容。agent 一个字都不改，也不移动。
- `<!-- facts:start -->` 与 `<!-- facts:end -->` 之间由 `wiki.py` 生成，每次收录都会重写。agent 不手改，要改就改原始层后重新收录。
- 其余正文由 agent 负责：可以重写、合并、补链接，保持准确简洁。
- frontmatter 的 `status`、`favorite`、`archived_from` 只通过 `wiki.py` 或网页修改。

## GitHub 结构化工作流（2026-10-27）

任务、评审与验收在 GitHub 私有仓库的 Milestone / Issue / PR 中进行，不再新建或维护文件形式的任务书；旧任务书（T1–T7、P1、P2、M1–M3、R1）与 `remaining-gaps.md` 经 `wiki.py gh migrate-legacy` 迁为 Issue 后只读停用。各子命令的参数、前置条件与仅本地运行的检查清单见 research-wiki 技能的 `references/github-workflow.md`。

- **项目自带、与宿主无关**：流程由本项目的 `wiki.py gh` 子命令、仓库内 `.github/`（PR/Issue 模板与 CI）和 pre-push hook 实现。Codex、Claude、Devin、Kiro 等任何 agent 都通过 `wiki.py gh` 遵守同一套规则，不依赖 Kiro 或任何宿主的私有配置。
- **两个仓库**：`research-wiki-dev`（`开发/`，代码与技能）与 `research-wiki-vault`（项目根，含本知识库、`文档/`、`tools/`），默认分支都是 `main`。主检出平时停在 `main`，作为 Obsidian 与 launcher 的阅读检出。
- **分支命名**：长期分支 `project/<课题>`、`ingest/<批次>`；任务分支 `task/<批次>-<阶段>-<主题>`，阶段为 `P0`–`P5` 或 `T<数字>`，批次与主题是小写 slug（≤ 40 字符），如 `task/scp-wave3-P2-harmony`。中文名称写在 Milestone/Issue 标题里。
- **Milestone / Issue / Label**：每个长期分支有同名 Milestone（`gh start-batch` 建）；每个任务一个 Issue（`gh start-task` 建），正文含 `rwiki-task` 标记与“目标 / 验收标准 / 本地证据 / 验收结论”四节，本地证据只写相对路径与 sha256。Label 分四组：`type:*`、`stage:*`、`status:进行中|待评审|需修改|已验收`、`blocked:*`。
- **PR 模板**：关联 Issue / 改动摘要 / 测试结果（CI）/ 本地专属验证 / 受保护字节核验 / 未完成项。`gh finish-task --local-report <文件>` 把仅本地运行的检查摘要填入“本地专属验证”，并把 `gh protect-baseline --check` 结果填入“受保护字节核验”。作者改了 user 块时，重新运行 `gh protect-baseline` 并在该栏写明。
- **分工**：编码 agent 负责 `start-task` → `save`/提交 → `finish-task`；评审必须由非编码 agent（Codex 角色）执行，并用 `wiki.py gh review <pr> --verdict pass|changes --findings <文件>` 回帖。编码 agent 不评审自己的 PR。回帖是 COMMENT 类型 review，正文首行为 `<!-- codex-review: verdict=pass|changes sha=<PR head 的 40 位 SHA> -->`。
- **Merge_Gate**：`wiki.py gh merge <pr>` 只在 CI 检查非空且全部 pass、最新一条 codex-review 标记为 pass 且其 sha 等于 PR 当前 head 时合并；PR 之后再有提交，旧评审即失效。不通过时 PR 保持未合并，回帖 `<!-- rwiki-gate: blocked sha=<head> -->`、原因与修复计划（`--plan`，缺省“待补”），命令退出 1。合并后自动关闭 Issue、标 `status:已验收`、释放写入锁并清理任务分支与 worktree。批次内 Issue 全部关闭后由 `gh close-batch` 开到 `main` 的 PR，同样经 `gh merge`。
- **本地门禁模式**：免费私有仓库没有远端分支保护（保护 API 返回 403，bootstrap 记为 `protection: local`）时，合并只能经 `wiki.py gh merge`，不在网页上点合并，也不直接运行 `gh pr merge`；pre-push hook 拒绝直接推送 `main`、`project/*`、`ingest/*`（新建长期分支且等于 `origin/main` 除外）以及任何 `legacy/*`。
- **pre-push hook 不入库**：新克隆或新机器先运行 `wiki.py gh install-hook --repo dev|vault` 重新安装。hook 调用 `gh guard`，拦截画廊、GPL 源码、课题数据、超限文件与本机绝对路径；`gh guard` 与 `gh protect-baseline` 是纯本地检查，不需要 gh。
- **save 与前端写入**：`main` 与长期分支上 `wiki.py save` 被拒（提示先 `gh start-task`），网页（`server.py`）的写入端点同样被拒，页面改动被还原。只有在 `task/*` 分支、由持有写入锁的 `RWIKI_AGENT` 执行时 save 才提交，提交附 `Issue`、`Agent`、`Pages` trailer。要在网页里编辑，先 `gh start-task … --worktree`，按其输出设置 `RWIKI_WIKI_ROOT=<worktree>\知识库`，再运行 `tools\launcher.ps1`（launcher 会把该变量以 `--wiki-root` 传给 server），UI 写入即落到任务分支检出。
- **GitHub 上的 vault 不含** GPL 源码目录（`知识库/.gitignore` 的 push-guard 托管块）、`画廊/` 与 `维护记录/`。CI 用 `lint --ci`，这些缺失报 `LOCAL-ONLY`、不计错误；完整 `lint` 与方法复核只在主检出或带 GPL 目录联接的 worktree（`start-task --worktree` 自动建 `mklink /J` 联接）中本地运行。
- **部署来源限制**：`tools/deploy.py` 只在 `开发` 工作区干净、HEAD 等于 `origin/main` 或恰为已推送 tag 时部署 5 处技能目录，manifest 记 `source_commit`/`source_tag`；首推前只能用 `--verify-only` 核对。
- **不要在主检出检出 `legacy/master`**：旧 master 跟踪了画廊与维护记录，检出它再切回会把这些未进新 `main` 的文件从磁盘删除，且远端没有副本。

## 操作

所有写操作的最后一步都是 `wiki.py save "<说明>"`：重建 index；有变化时追加 log 并提交到当前任务分支，没有变化时什么也不做。`ingest-figure` 已经包含这一步。save 只在 `task/*` 任务分支上提交（`main`、`project/*`、`ingest/*` 上拒绝，见“GitHub 结构化工作流”）；git stage/commit 限定在 Wiki 根目录子树（`git -C <wiki_root> -- .`）：Wiki 是更大仓库的子目录时，兄弟路径的已暂存/未跟踪改动保持原状，不被 Wiki 提交裹挟。

### 后续入库八步（2026-10-23 追加，方法和来源通用）

1. **读输入与目的**：先读资料、数据说明、代码和已有计划，明确分析目的、输入语义、输出对象、统计单位、估计目标与本次提炼范围；同时确定研究领域与候选分析用途；复用作者已确认的答案。
2. **查库与语义去重**：必须查现有方法家族、实现、流程和接口。按研究问题、输入语义、行/样本单位、估计目标和算法假设判断是否同一家族，不只比标题、函数名、关键词或来源包；字段名相近不自动认领，来源不同也不自动新建。
3. **分类判定**：同一实现补来源/修订；新算法/实现加入已有家族的分支；多个方法串联记为 `workflow`；源码/环境/绘图适配记为 `technical`；只有新的分析目的才提议新建家族。参数变化是配置，不新建家族。`analysis` 家族按正文依据补一个或多个受控 `purposes`，不为了填满分类夸大范围。
4. **具体收录方案**：列出要更新的页面、增量、函数入口、验证、材料缺口、输入语义、内部接口、可选表/列及依据、bindings 与关键选择；关键选择明确后执行。缺原始数据、改变统计逻辑、补缺失算法或把某列声明为可选先问作者或说明实现证据。
5. **提炼**：原始代码保持原语言/原字节；提炼版独立，显式数据/参数/结果/诊断，说明复制依赖和调用方式；只在现有环境验证，本轮不安装包。先读语义再绑定：外部表只在显式映射层整理，不改原表。同时确定最小调用闭包、算法包、转换层、局部资源、可选分支和复制清单，写入 `runtime.json`；不能拆解时明确标 `bundle`/`unknown`，不以整库加载器冒充独立实现。
6. **验证**：逐实现实际调用原版/提炼版、异目录复制、换合法数据和输入不变检查；失败/缺依赖/未运行写精确 `not_run`，不以加载或一个分支通过批准整个家族。独立迁移另做：只复制清单文件/资源到异目录，不提供来源库路径，在新进程实际调用，记录命令、环境与闭包哈希；算法等价用原版/新版同输入对照。新增/改变 bindings 时另做原输入与绑定输入的表/图对照；旧标准输入收据不扩大为任意外部文件已验证。
7. **知识整合**：编译进已有知识，更新实现选择、适用边界、相关方法/流程/接口/图样；来源冲突时记录并修订旧判断，不做一来源一孤立条目。
8. **验收与确认**：检查重复、断链、冗余与证据，更新带摘要索引和只追加日志；知识整理、算法验证与独立迁移分别显示，按正常作者确认流程交付。`check-entry` 核对运行清单、独立性收据和算法收据的当前指纹；未验证知识默认可读但明确标注，不能作为可执行推荐。

**跨来源去重要求**：青光眼与 SCP 的同义分析汇入同一规范家族；同一算法不同包装是实现/适配差异；不同算法可同家族但必须比较输入、假设、单位和结果，不能当可互换；旧页保留 id/来源/备注并指向家族。自动 `lint` 只检查声明结构/标题重复/收据结构，跨来源语义同义性必须由 agent 按本流程人工审查，不能宣称自动解决。每次实质入库交付“旧页/来源→规范家族→具体实现→原始来源”对照表。

### 来源 panel 存储（2026-10-23 追加）

- 来源 panel、完整原图、`original_code/` 属于画廊等只读原始层；前端通过受控路径读取，不要求复制到知识库。
- Markdown 只保存来源路径、哈希、裁图/bbox 与证据链接；新增入库不得重复存放同字节来源图片。
- 模板/方法资产目录可保存可复用代码、示例及真实回放预览；来源图片与这些资产角色不同。
- 没有回放预览时允许显示来源 panel，但必须明确“来源参考图／尚无回放”，不能冒充模板运行验证。
- 验收：从画廊读取来源图可展示；Wiki 无新增重复来源图；参考图与回放图标识正确；原始哈希不变；不为满足规则擅删历史资产。

### 收录（ingest）

1. `wiki.py ingest-figure <entry_id>`：建或更新版式页骨架、补齐图型页、提交。受控大类从画廊 `scenarios.primary/secondary` 带过来，`scenarios.free` 进入 `keywords`；`tags` 只用受控词表中的规范键。
2. 读画廊条目的 README、`qa_report.md`、`figure_spec.json` 和原帖 `source.md`，核对实际范围：单 panel 的 `source_image` 是选定裁图、`source_image_sha256` 是裁图哈希；完整原图另存并记录独立哈希/bbox。填写版式页的“适用”和“不适用”：所选图样回答什么问题、需要什么数据、什么时候不该用它。写有依据的用途，学科背景可写入 keywords，不据此限定或夸大适用性。新 layout 页只代表一个选定逻辑 panel；收录前核对 panel_map 恰好一项。完整原图不进入新 Wiki 条目。
3. `wiki.py save "ingest <id> 说明"`。

### 收录后的配图、范围与知识关联

新增/实质更新方法或图样后，双向检查“一方法多图／一图多方法”，包括不同来源。核对目的、语义、行单位、量纲、前提与代码状态，有依据才写 figure_relations（方法侧唯一记录）。状态为 direct/adaptable/candidate，分别为直接可接/需要适配/待核实，另写 verification 的状态、范围、证据。来源图样不能 direct；接口 feeds 只表示结构匹配。方法页/图页/图谱从同一记录派生；归档不再推荐，删除清理关系并审计。正文记录检查范围、依据和未关联原因。详见 research-wiki 的 references/knowledge-linking.md。

图库仅按单panel图样、可调用模板两栏区分。新layout只容纳单panel来源；历史整图归档隐藏。逻辑panel数而非axes数决定来源范围。图片、状态和范围都需在前端实查，逐一检查已有单panel函数模板能在图样入口找到。n为任意合法数量，由课题agent编排；文档中的能力标准不代表所有历史模板已经适配。

### 收录后的编译：接口含义与图型判断（2026-10-22）

Wiki 存的是编译后的理解，不是原始文件的副本。一次 ingest 不应只改 layout/template 两页；至少检查并更新下列页面，没有可写内容时说明原因。

1. **接口页 `## 含义`**：每个被模板读取的接口必须写一段，不能只留列名。至少写清：一行代表什么（行单位/粒度）、单位或编码（如 0–1 与 0–100、log 尺度、缺失含义）、准备数据时最容易出错的前提、与相近接口的区别。模板不重算的统计明确写“上游给定/模板不重算”。`lint` 对含义为空报 WARN。
2. **图型页**：`chart-types/<slug>.md` 是概念页，不是标签页。统一写五节：`## 回答什么问题`、`## 什么时候选它`、`## 什么时候不要用`、`## 与相近图型怎么区分`、`## 常见误用`；有模板时加“本库模板”链接，没有模板时明确写“本库暂无模板”，只写保守的通用判断。`suggest` 仍读模板/方法页的“适用/不适用”，不读图型页正文；图型页用于 agent 选择和解释，不替代推荐逻辑。
3. **方法关系页**：按“收录后的配图、范围与知识关联”检查 `figure_relations`；接口页的“产出/读取/经模板关联的方法”由 `save` 派生，不手写。
4. **项目与查询经验**：课题中得到的判断、失败模式、适配动作，先登记为课题状态层 lesson 草稿（`project add-lesson`，≥1 条已登记证据引用；同命题同范围自动合并）；经署名 `lesson-review`（accepted 须附已登记 `decision:` 作者决策）后仍走正式 Wiki 评审，回填到 `projects/<slug>.md` 或相关页面“使用记录”，不留在对话里。accepted 草稿只是候选提案，不是已入库知识；deferred/rejected 永不进正式推荐。项目页只写用了什么、怎么适配、出了什么问题，不复制课题数据或成图。
5. **不复制原始层**：来源 panel、整图、缩略图和哈希留在画廊；Wiki 页面用链接、画廊路径和证据指针，不把图片副本写入知识库目录。前端 preview 从画廊读取来源 panel，缩略图明确标为复刻缩略图。

判据：下一个 agent 读完这页，是否会做出不同动作？会，写进页面；只是“知道有这回事”，链接到源即可。

### 处理待办：拆 panel 与模板化

作者签核后版式变为 pending_template。作者说“处理待办”时：

1. `wiki.py pending` 列出尚需agent处理的来源；先查关联模板，继续已有草稿或补缺口，不重复新建。
2. 按选定样式处理，不按图型名机械合并。一个代表单 panel 一个条目；inset、色标、边缘分布属于该 panel。结构变体默认在不同条目中保留，现有 `<条目 id>--<图型>` id 无需扩展。同条目的历史组图若存在同图型不同结构，不能为适应 id 冲突强合并；记录具体限制再决定最小处理，不自动重做旧图。
3. 先查已有 ready 模板，核对数据接口、编码和附属元素；相同画法用 `attach-template` 复用，实质不同才 `scaffold-template`，写清差异。模型/指标名或颜色变更不自动新增模板。
4. 按下述函数契约处理代码。`code/` 包内相对导入；保留 `panel.py` 的 `draw(fig, rect, tables, style)` 适配，在给定区域作画，可调视觉参数放 spec.style。独立调用、render 和组图共享绘图核心。
5. 每个模板 `verify-template` 单独回放，对照选定裁图检查并交作者确认；确认后 `mark-ready <模板 id>`，即可独立 `render` 并换数据检查。这个链路不依赖 `verify-layout`，来源 layout 此时仍可为 `pending_template`。
6. 若还要将来源 layout 标为 `ready`，须为它准备自己的 `layout.json`、覆盖本条目已选 panel 的布局和 `preview.png`，运行 `verify-layout`，交作者确认后再 `mark-ready <版式 id>`。选定 A 单 panel 时使用只含 A 的 1×1 布局与覆盖，绝不要求未选 B；不再制作整组回放或要求未选 panel。测试或回放不自动推进作者签核。

### 接口

- 接口按数据本身定义，与模型和工具无关：“SHAP 汇总表”是一个接口，不分 XGBoost 还是随机森林。
- 新建前先找已有接口：`scaffold-template` 会打印列名相同的接口，能复用就复用。确需新建时用 `add-interface`，并在“含义”节写清一行代表什么、与相近接口的区别。
- 模板 spec 的每张表写 `interface`、`description`，可写 `required:false`；接口列可写 `required:false`，未写默认必需。标准输入文件名为 `<接口 slug>.csv`，这是内部执行约定，不是作者原表要求；不给 bindings 时保持旧入口。分析函数返回表，显式调用层可写成标准文件交 `render`，内存表也可直接传绘图函数。接口相接只是候选条件，仍须检查方法前提。
- 可选只用于实现确实有缺省分支的表/列；不能为了绕过检查把核心仍索引的列改成可选。缺可选项时只允许走已声明的默认分支，并报告省略/缺失，不补 p 值、样本、均值或分数。

## 灵活输入与三层契约（2026-10-23）

- **语义层**：方法家族写清需要什么对象/矩阵/模型、行单位、配对关系、编码/单位和前提（`data_contract` 与正文），不强制 CSV。
- **实现层**：具体实现写真实接受的对象、参数、依赖和返回结构；已有 Seurat/模型纯函数入口继续有效。
- **执行层**：绘图函数消费已分析结果；内部接口是代码约定。外部课题数据在课题副本用显式 bindings 映射为内部标准表，再由现有 R/Python 绘图核心消费。
- CLI：`wiki.py render <template> --data <dir> --bindings <bindings.json> --out <dir>`。`columns` 方向为“内部字段 → 作者列”；`file` 相对 `--data`，不允许越界、网络地址或隐藏路径。未知表/字段、重复映射、重复源表头、非法数值、必需表/列缺失在运行前失败，不按字符串相似度猜列。
- 只允许无聚合的长宽整理（显式 melt/pivot，写清 id、变量列、值列）；pivot 重复键拒绝，不自动求均值、不补格。pivot 的 index 必须按原值身份保留（空字符串、缺失值、嵌入分隔符值原样输出），空/缺失的 pivot 类别显式拒绝。
- 检查完整有效映射（显式映射 + 同名回退）；同一作者列只能被一个内部字段消费，冲突要报出具体字段，不能靠同名回退掩盖必需语义缺口。
- 写前预检全部来源与全部输出：输出不得覆盖任一源文件（同名、另一个表的输入、硬链接/符号链接别名）。源哈希在任何写操作前采集；所有规范表先 staging，全部成功后才替换正式输出，失败不留部分结果。映射报告写入课题输出目录，含源路径/写前哈希、映射、整理操作、缺失可选项和检查结果；不向 Wiki 写课题数据。
- 字段名吻合不证明单位、粒度或配对已核实。0–1/0–100、不明单位或粒度不一致必须提示并由 agent 核对，不自动换算；不编造 validator 已知事实。
- 可复制适配核心：`rwiki/input_binding.py`（Python，仅标准库）与 `assets/input_binding.R`（R），用同一夹具核对等价；调用方式与边界见 `references/input-binding.md`。旧标准 `render`/`verify`/单 panel 回放保持兼容。bindings 只用于单模板 `render`；`render-layout` 组合入口仍读全部面板表。

### 收录方法（写方法笔记）

> 先完成“后续入库八步”并通过语义去重：同一实现/算法优先补来源或分支，只有确认是新分析目的才新建家族。不要第一反应 `scaffold-method`；新家族/新实现方案明确后再写页面。

1. `scaffold-method <id> --title … --license …`，来源选一种：`--from-entry <画廊条目>`（帖子代码）、`--from-path <路径>`（作者课题脚本；GitHub/论文代码加 `--url --commit`，下载前须征得作者同意）、`--written`（依据文献或官方文档编写）。原代码复制到 `source/`，不改。
2. 一个方法页可表达有边界的方法家族；写清核心目的、来源具体实现、成立条件、已有代码分支、限制与未验证分支。按实际数据条件和实现边界说明工具/模型适用性；不能为支持“任意模型”强改算法。预处理与分析分开写；前后接口兼容且方法前提满足时才串联。只有联想而无代码的方法先保留文字，不自动实现。
3. 写正文各节：
   - **用途**：做什么、结果是什么。
   - **适用 / 不适用**：数据前提（样本量、变量类型、任务类型）、什么情况会得出误导结论。
   - **输入**：需要什么数据、每行代表什么、哪些列。
   - **怎么做**：步骤；作者数据不同时要改的地方；方法前提、必要诊断及结果限制，避免无依据的通用判断。
   - **代码**：有来源代码时按下述契约放修改副本进 `code/`，写函数签名、参数含义、依赖、限制和验证状态；没有则明确“文字笔记/未实现”，不强制补代码。包依赖在这里说明，不在知识库里装环境。
   - **输出**：最后怎样整理成哪个接口表（列名、每行含义），frontmatter 的 `outputs` 同步写接口 slug。
   `license` 不明时写 `none`，页面会显示“仅供个人研究参考”；`cite` 只写能核实的文献。
4. 写完交作者确认（网页“确认”或 `mark-ready`），确认后才推荐。

### 有来源代码的函数契约

- 记录原语言、来源/许可证或未知状态、原字节及 SHA-256；源代码只读，函数化修改版独立，列原函数与新入口映射。普通路径/输入输出整理和参数化在已确认计划内可做；改变统计逻辑、估计量、泄漏边界、缺失值/异常值算法，替换或补缺失分析算法前，说明具体差异并询问作者。
- 分析函数显式接受数据对象、变量/结局/分组列、算法实际需要的参数和随机性，返回结构化结果表及必要诊断，记录列/类型/每行含义。默认不隐式读写、绘图、联网、安装或修改知识库；原算法必要副作用明确隔离和记录，不能静默删除。
- 绘图函数消费表，显式列映射与视觉参数，不隐式训练或重做分析。按原语言传入/返回可组合对象：Python 通常为 figure/axes，R 为适合的 plot/grob。边缘分布等多 axes 仍为一个逻辑 panel，导出由显式调用层处理。
- 复制所需模块到作者课题，用课题自己的 Python/R 环境；数据、列和必要参数显式传入，不依赖原工作目录、硬编码路径、知识库目录或全局临时变量。保留 render/draw 适配，共用绘图核心；分析和绘图可独立或串联。不要求制作全局 pip/R 安装包。
- 每个实现/模板在资产根写 `runtime.json`：入口、运行模式、复制文件、资源、必要/可选包和来源映射。独立性证据放 `verification/`（模板也可 `verify/`），记录异目录、新进程、命令、环境和闭包哈希；不得用 source 成功、文件存在、假引擎或整库 bundle 收据冒充独立迁移或算法运行。
- 实际比较原版与封装版数值结果、行顺序、缺失值处理、随机性和图形结构；必要容差说明依据。检查不同工作目录、复制到课题后换数据的可移植性，记录命令/环境/结果。未运行项目标未测，不能把单例通过扩大为任意数据、模型或科学有效性。


### 数据规模适配也是函数化验收的一部分

这里 n 是依据课题既定分组定义从实际数据识别的任意合法组数（正整数），不设固定数量白名单，不为每个 n 写分支或另建模板。agent 在做课题时自行绑定数据、识别 n，并按图型、标签、附属元素和版面要求编排尺寸、留白、配色和位置；每项宽/高等默认系数只是可覆盖初值。不得擅自改变研究分组含义来适应图形。作者已指定的样式/尺寸限制继续遵守；未指定时按既有单panel、可读字号和间距原则执行。

函数化须能适应同类场景的数据结构变化，不只是把原脚本包进函数。分组/类别/系列数量、顺序、标签、配色和位置从显式输入或数据获取；不把原图六组、固定模型名或固定列数写成复用限制。分析函数仍遵守自身算法前提，不为支持更多组而自动改变统计方法。

绘图先声明尺寸驱动：纵向分类图按类别数加宽，横向条形图按条目数增高，矩阵按行列数调整；散点不因样本数增多而无限放大，必要时使用固定比例。规则例如 W=左右留白+n_x×每项宽度、H=上下留白+n_y×每项高度；系数与物理单位由模板说明、参数化，长标签可增加所需空间。字号和最小组间距保持可读，不能靠缩小字体掩盖拥挤。

默认保持一个逻辑panel、保留间距并继续加宽/增高；max_width_in/max_height_in默认null。只有作者明确设置尺寸上限，才在超限时报告所需/允许尺寸并询问方案，不自动截断、压缩、分面或隐藏类别。布局须同时检查标签/图例/色标及配色是否足够；不得对离散组静默循环有限色板。

原图复刻用replica/fixed模式保留显式宽高及原图比例；换数据用adaptive模式，验收宽高增长、间距和文字，不拿原图宽高比阈值约束自适应复用。调用方可显式覆盖参数。组图draw(fig,rect,tables,style)尊重外层画布，不能自行resize；空间不足应交调用层扩大布局或询问作者。

新Python模板的spec.style.sizing从research-wiki config.json的function_defaults.sizing快照，随code/sizing.py复制到课题；配置优先级为调用覆盖>模板快照>建模板时的全局默认。默认profile=unbound，agent必须确认实际表/列和方向后绑定，不凭图型名猜数据含义。函数与render共用同一尺寸/绘图核心，输出解析后的尺寸记录。Python实现及完整例子见research-wiki的references/adaptive-sizing.md；R保留原语言并实现同等行为，不能把Python验证写成R已验证。

验收覆盖代表规模变化：由agent按模板和课题选择若干不同组数及适当边界案例，另测不同样本数、长标签、显式顺序/列映射、配色不足处理、手动尺寸与用户上限；横向图/矩阵检查相应维度增长。比较数值和行序不变、无输入修改、图形数量正确、物理组间距不缩小、文字无裁切；复制到另一目录换数据实际运行，独立入口和render/组合入口分别记录。仅测试原图规模不算完成规模适配。历史模板逐一记录legacy/适配状态，不因新规则自动宣称已迁移或批量改历史图。

### 查询与推荐（query）

1. 先读当前课题必要计划、数据说明、代码、结果表头与运行证据，明确研究目的、样本/行单位、验证设计、当前阶段及未知项。代码存在不证明已跑完；缺目的或关键条件先问作者。不由网页服务器扫描任意课题目录。
2. “课题还能做什么分析”：用 suggest-methods 查 ready 方法，不限是否已有配图；优先少量当前可做项，再给少量有价值且能说明缺哪些材料的候选。说明用途、项目依据、前提、缺口、代码存在/验证范围、可配图样。无合适库存就如实说明。
3. “分析已跑完选图”：先核对结果语义/粒度/量纲/重复层级，再 suggest 查单 panel/模板；不必新增方法。接口/列名不同不能是发现的唯一排除条件，同名也不证明直接适用。suggest-pipeline 结合关系提供候选，agent 仍须读正文。同一张图有多种可接方法时，列对比（各自适用什么数据、作者数据是否满足）并给出首选与理由，由作者决定。
4. 有现成选择与计划就复用，否则等作者选定。含义清楚且不改分析逻辑时，课题副本可映射列名、列顺序、文件名和长宽表；原表不改，继续通过执行入口的严格检查。核对源哈希、主键、值、实体、单位与转换可还原；不能要求长宽转换总行数相同。
5. 未知单位/指标定义、重复身份不清、缺关键材料，或涉及聚合/删行/填补/补样本/重算统计量/单位换算/阈值或验证设计改变，说明具体差异先问作者。缺包也先问，不在 Wiki 装包或换 Wiki 环境代跑课题。
6. 选定后复制代码到课题，用课题环境运行、检查前提/诊断、出图。**仅当任务授权明确包含正式 Wiki 写入时**才 `record-use` / `record-method-use`——两者都是正式 Wiki 写并可能提交 Git，与只写课题目录的 `project record-run` 完全不同：授权只含隔离实验或明确禁止正式写时不要调用，证据留在课题状态层与 lesson 草稿；图完成或运行登记本身不构成回写授权，明确任务边界优先于通用流程步骤。record-method-use 核实已完成运行的收据结构+产物/输入指纹现行才登记，不配图。登记运行/使用时写清代码来源是 Wiki 分支还是课题自有：用课题自有代码运行或仅整理/格式化既有结果，不能记成"运行了 Wiki 实现"；真正的实现复用是选科学兼容的已验证分支、按其 runtime.json 复制声明文件/资源、在新进程用显式输入/参数调用所复制入口并保留范围与诊断，受托管 render 或课题内准备脚本不构成实现运行证据。家族/实现绑定按实际执行的操作、输入输出、单位与算法判定：消费既有标签/预测/结果文件不等于执行产生它们的算法（评估既有预测≠训练、绘制构象≠对接、汇总既有标签≠聚类）；无匹配规范家族时用未绑定课题任务加显式来源，库内缺口如实保留，不为通过核查新建正式家族。检查项与检查者如实写入收据；无图像读取能力时目视检查标待办并写明由谁核查，不记未做过的目视确认。无算法的文字笔记不授权补算法。方法/图关联直接可接不证明当前课题统计有效。
7. 课题证据层用 `project` 子命令写 `<课题>/wiki-use/_project/`（对象/观察/任务/运行收据/经验草稿；只写课题目录，不进 save 链）；`record-run --code` 登记实际代码来源，复用已完成运行依赖它判定"同一计算"。运行证据/适配记录同时可留 `<课题>/wiki-use/<本次标识>/` 的 context、recommendations、mapping。项目映射先留课题；有通用价值时经 lesson 草稿与正式评审回存，作者再次确认才入库，不覆盖原版或污染全库接口。详细模板见 research-wiki 的 references/project-reuse.md 与 project-state.md。

### 原生代码与网页查看

原生 source/ 与复用 code/ 分开，语言/字节/来源/许可证/哈希保留；原文片段不能标成完整原版。方法、单 panel 图样、模板卡片的“查看代码”在 Wiki 内显示版本和文件，支持复制/下载，仅只读查看。未知编码或二进制原字节下载，不运行网页代码或 Notebook 输出，不增独立代码分类。枚举真实文件，无代码如实说明。代码存在、页面 ready、关系兼容与实际验证范围独立。详见 research-wiki 的 references/code-assets.md。

### 体检（lint）

`wiki.py lint` 报告断链、frontmatter 不合规、页面与画廊状态不一致、空白的适用说明、非法/缺失的 `purposes`、可选表/列声明问题。逐条修复（能改页面的改页面；属于原始层的问题报告给作者），然后 `save`。


### 归档条目的删除与预览

网页归档区和详情可先查看删除范围，再由作者明确确认永久删除 Wiki 页面及其专属资产；自动清理 agent 正文、元数据与布局中的关联，记录到 deletion-records，原始画廊保留。操作不可从网页恢复，Git 历史不作清除。后端仅允许 archived 状态，并核对确认时的内容版本；他页作者备注引用须由作者先处理，不能自动改备注。agent 不因作者要求“加删除功能”就代删正式条目。

预览以实际存在的资源为准。模板没有回放图时可显示对应单 panel 来源缩略图，明确标“来源参考图 · 模板尚无回放”；没有可用图时显示暂无预览，不请求不存在的 preview.png，不以来源图冒充已验证模板。

## 状态

版式：

| status | 含义 | 谁来推进 |
|---|---|---|
| pending_signoff | 画廊条目尚未签核 | 作者在网页签核 |
| pending_template | 已签核；模板进度按有效覆盖派生 | 作者说“处理待办”时 agent 处理 |
| ready | 选定单位模板就绪，且本 layout 的覆盖与 preview 经回放、作者确认；可按其版式套用 | — |
| archived | 已归档，不再推荐；`archived_from` 记录原状态 | 作者在网页恢复 |

panel 模板：

| status | 含义 | 谁来推进 |
|---|---|---|
| draft | 已拆出，代码与回放待完成或待作者确认 | agent 回放，作者确认后 `mark-ready` |
| ready | 可单独套用 | — |
| archived | 已归档 | 作者在网页恢复 |

分析方法：

| status | 含义 | 谁来推进 |
|---|---|---|
| draft | 笔记待完成或待作者确认；或被作者退回（log 有理由） | agent 写完后作者在网页确认或 `mark-ready` |
| ready | 作者已确认笔记；是否作为可执行分析推荐另看实现收据 | — |
| archived | 已归档 | 作者在网页恢复 |

`ready` 不是执行许可：`analysis` 还需当前 `verified` 实现；`workflow`/`technical` 可确认资料但不进入分析方法推荐。只运行了加载、假引擎或合成夹具，不写成算法/科学验证；`not_run` 分支保留精确原因，不能用一个通过分支批准整个家族。

## 写作要求

- 页面写给作者和下一个 agent 看：事实优先，短句，不写套话。
- 不编造数据、文献或适用结论。不确定就写“待作者确认”。
- 不复制原始层的大段内容，链接或引用路径即可。


### 页面命名（2026-10-22）

- `id` 是业务键、文件名和引用键；不因标题调整而改名。现有 id 冻结，新条目仍用 `<layout-id>--<chart-type>`。
- `title` 是给人看的内容名，中文为主，保留 UMAP/SHAP/marker 等必要术语；约 8–20 字。
- layout title = 图样名（必要时加来源限定，如 GSE 号）；不写 `单panel：`、`图表复刻`、原帖标题。
- template title = 可复用功能名；不拼 `<chart_type> · `、layout title、项目名/来源/版本/`示例数据`/`图型`。`scaffold-template --title` 显式传入。
- method title = 对象 + 核心操作 + 必要限定；来源、commit、license 写 `source` 与 facts，不写进标题。
- 同一信息只出现一次：图型在 `chart_types`，项目/来源在 facts/keywords，panel 在 `panels`。
- 画廊卡片标题用页面 `title`（或 `figure.label`）；不把 `post.title` 拼进 layout/template 标题。

### 待办按剩余动作派生（CLI 与前端共用）

持久 status 表示来源签核/版式回放或模板确认阶段，不等于当前谁还有工作。后端只读 workflow 统一判断：

- 已签核来源尚缺有效模板覆盖：agent核查缺口、归档或关联，保留已完成部分。
- 已有草稿但无完整成功回放：agent继续该模板，不重复scaffold；来源不重复算一项。
- 草稿已有成功回放记录和对应输出：交作者确认，列入“待你确认”，不列agent待办；代码改变后仍应重新verify-template并核对回放，文件存在不证明科学有效。
- 所选panel已由ready模板完整覆盖：来源显示“模板已就绪”并退出待办，即使其status仍为pending_template。来源可选layout回放与单模板可用性分别记录。
- 待签核来源/新版本仍交作者签核；回放不自动确认。归档/删除模板导致覆盖缺失时重新派生待办，恢复后重算。

`pending`只列尚需agent处理的来源ID（包括已有未完成草稿）；先检查关联模板与当前说明，不见pending_template就重新拆模板。重复ingest或刷新不会新建待办记录或推进状态。不得为了清零而伪造layout验证、作者确认或删除来源。

SHAP和回归评估仅是同一验收标准的不同例子：前者的已声明输出表对应三个历史绘图模板；后者有两个绘图模板，但要另准备同源RGB/边缘表或选定指标与摘要，仍标需要适配。例子的图数、模型名和列名不是后续入库的固定要求。

### 入库验收的执行入口（2026-10-21 修复）

- 来源读取版本 `gallery_version` 与作者已签版本 `signedoff_version` 独立。网页签核记录当前来源版本；新版本反复 ingest 都保持待签核，刷新不能代替作者签核。来源在页面读取后又更新时先重新收录核对。历史已确认来源保留其原签核事实，不因迁移虚构新确认。
- `verify-template` 的成功记录绑定当前 code、spec、示例数据、接口列定义和 PNG/PDF/SVG 输出哈希。修改这些输入、替换输出或失败重跑均使旧回放失效，旧记录保留历史。未绑定哈希的旧回放不作为当前执行证据；先用原代码/原示例重新 verify，不改算法或伪造记录。回放环境与范围另记，不能证明所有依赖环境或科学有效。

- 方法、模板及来源正文都写“知识关联检查”：日期、查过的页面/范围、一方法多图与一图多方法判断、依据/限制、无匹配原因。机器核查该节和其他必需节不是空白/占位，并检查已声明关系结构；科学语义仍由 agent 核查，不把文字存在当成科学验证。
- 公开 `check-entry <id>` 查询当前缺项；核对完成后 `check-entry <id> --record` 保存 `acceptance.json` 和 Git 记录。确认入口也自动保存相同验收记录。记录内容指纹、已检查节及回放范围，不推进作者状态、不证明科学有效。实质更新后重新检查，作者区块、facts、标签/收藏与验收内容分开。

### 链条完整性与读取接口（2026-10-22）

- 方法页“接口结构匹配”必须显示结构匹配模板；若没有直接消费声明输出的模板，必须另列“语义关联的模板（需适配）”，不能只留“暂无”。
